# 0033: Dependency-update policy — dev tooling only, grouped, gated by audit

- **Status:** accepted
- **Date:** 2026-09-19

## Context

The runtime dependency surface is deliberately zero: nothing in `core/` or `installer/src/` imports
an npm package. The npm tree that does exist (`tools/`, `test/`, `config/`) is build/test tooling,
and unreviewed tool churn there can silently change generated bytes (see ADR
[0032](./0032-pinned-build-toolchain.md)) or break the gates. The policy lived only as a
`dependabot.yml` comment mis-attributed to ADR 0017 (the required-check contract).

## Decision

Dependencies update through Dependabot: a weekly, grouped minor/patch npm pass (one reviewable PR,
`open-pull-requests-limit: 5`) plus weekly pinned-Actions SHA updates, and
`pnpm audit --audit-level=high` in the `checks` job as the audit gate. Major bumps of anything are
never automated — they are deliberate, reviewed changes (toolchain moves are ADR 0032 manifest
edits).

## Consequences

Security patches land within a week without per-package noise, and every bump is one grouped PR to
review or reject as a set. The cost: a single grouped PR can mix unrelated bumps, so a bisect for a
tooling regression starts by splitting the group. Runtime-dep requests should be refused by default
— adding one is an architecture change, not a dependency update. Revisit-if a runtime dependency
ever becomes necessary.
